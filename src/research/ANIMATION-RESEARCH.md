# FC 온라인 애니메이션·모션 재현 조사

조사일: 2026-09-22. 목표는 FC 온라인의 자세·이동·접촉·전환 타이밍을 관찰 가능한 수준에서 동일하게 재현하는 것이다. 이번 결과물은 공식 자료 38건, 공식 영상 주소 200개, 현재 축구 프로젝트의 모션 코드 및 캡처 데이터 검사다. EA의 비공개 소스나 원본 애니메이션을 추출한 결과는 아니다.

## 1. 이번 조사에서 가장 중요한 결론

달리는 장면 하나를 그럴듯하게 만드는 것과, 달리다가 공을 받아 방향을 꺾고 즉시 패스하는 장면을 똑같이 만드는 것은 작업량이 다르다. 후자는 **동작 데이터, 동작 선택, 이동 경로, 접촉 시각, 전환 가능 시점, 최종 관절 보정**을 함께 맞춰야 한다. 이 여섯 가지를 서로 따로 조절하면 자세는 좋아도 발이 미끄러지거나, 공이 먼저 출발하거나, 입력 뒤 불필요한 준비 동작이 생긴다.

FC 온라인에서 정식 반영을 확인한 비교 기준은 **2026-03-26의 12차 Next Field**다. 큰 방향 전환, 양발 활용, 골키퍼와 패스 차단, 일부 개인기 변경이 공식 페이지에 있다. 이것이 2026-09-22 현재의 모든 후속 수정까지 대표한다는 뜻은 아니다. 재현용 영상은 촬영 당시 패치를 따로 기록해야 한다. [공식 3월 개발자 노트](https://m.fconline.nexon.com/news/play/view?n4ArticleSN=48)

문서를 읽는 기준은 다음과 같다.

| 표시 | 의미 |
|---|---|
| FCO 확인 | FC 온라인 공식 설명에서 확인된 동작이나 변경 사항 |
| EA 비교 | 다른 FIFA/FC 또는 EA 발표에서 확인된 기술. FCO 채택 여부는 별도 |
| 자체 검사 | 현재 `apex-football` 파일에서 직접 확인하거나 계산한 값 |
| 재현 설계 | 공개 근거를 바탕으로 제안한 구현·측정 방법. EA 내부 설계라는 뜻이 아님 |

## 2. FC 온라인 공식 설명으로 확인되는 구조

### 턴은 단순한 캐릭터 회전이 아니다

12차 정식 안내에는 큰 턴에서 추가 터치와 후속 대기를 줄이고, 해당 상황의 아웃사이드 동작을 제외하며, 상황에 맞춰 양발을 사용할 수 있게 한다는 내용이 있다. 수비 차단은 새 동작과 경로·시각 예측을 함께 조정했다. 개인기에서도 질주 중 드래그 백용 동작을 추가하고, 공과 떨어져 있을 때 엘라스티코가 다른 동작으로 선택되는 문제를 다뤘다. **입력 명칭이 같아도 맥락에 따라 선택되는 모션이 달랐다는 직접적인 근거**다. [12차 정식 상세](https://fco.vod.nexoncdn.co.kr/list/2026/3/note_FCO_260326_v3hp6S2pq.html)

재현 설계: 턴 동작의 식별자는 최소한 진입 속도, 공의 상대 위치, 회전 각도, 공을 만질 발, 현재 지지발을 포함해야 한다. 몸의 방향만 180도 바꾸는 구현으로는 원래의 터치 순서를 표현할 수 없다. 정확한 각도 경계와 비용 가중치는 공개 자료에 없으므로 영상으로 구간을 찾아야 한다.

### 입력을 받은 순간과 동작을 바꿀 수 있는 순간이 다르다

2023년 개발자 노트는 퍼스트 터치가 내부적으로 녹온 드리블로 분류되며, 이미 트래핑을 시작한 뒤 늦게 방향을 바꾸면 새 방향으로 즉시 전환할 수 없는 경우가 있음을 설명한다. 이는 모든 프레임에서 자유롭게 모션을 바꾸는 구조를 가정하면 안 된다는 근거다. [퍼스트 터치 개발 설명](https://m.fconline.nexon.com/news/play/view?n4ArticleSN=37)

재현 설계: 입력 수신, 입력 승인, 준비 동작 시작, 동작 변경 마감, 접촉, 다음 행동 허용을 서로 다른 이벤트로 기록한다. ‘딜레이 0.2초’ 같은 하나의 값으로 묶으면 원인을 구분할 수 없다. 이미 접촉 직전인 동작을 바꾸기 어렵다는 사실과, 처음부터 입력을 버리는 버그도 구분해야 한다.

### 반응 판단과 모션 선택도 분리된다

12차 테스트 설명은 골키퍼의 반응 상황과 적절한 선방 동작 선택 문제를 다뤘다. 2차에서는 넓게 돌아가는 턴과 새 동작의 연결, 특정 거리에서 차단 모션이 제한되는 현상을 추가로 조정했다. 테스트 당시 설명이므로 정식 적용은 3월 문서와 대조해야 한다. [2차 테스트 개발 설명](https://fconline.nexon.com/news/notice/view?n4ArticleSN=5802)

재현 설계: 실패를 ‘AI가 반응하지 않음’, ‘후보 모션 없음’, ‘후보는 있으나 도달 불가’, ‘접촉 이벤트가 늦음’으로 나눠 기록한다. 같은 멈춤 화면처럼 보여도 수정할 계층이 다르다.

### 첫 터치는 별도 모션 계열이다

11차 자료에는 지상에서의 첫 터치 방향과 공중볼 처리 방식 변경, 아웃사이드 슛 사례 등이 실려 있다. 받기 전에 이미 뛰고 있는지, 공이 어느 높이로 들어오는지, 다음 입력이 무엇인지가 관찰 항목이다. [11차 공식 자료](https://fco.vod.nexoncdn.co.kr/list/2025/6/note_FCO_2506_mnkr2iCkvVk.html)

공식 체감 설명에서도 공의 강도·위치·입력 시점 때문에 논스톱 대신 먼저 제어하는 경우를 설명했다. [2022년 플레이 설명](https://m.fconline.nexon.com/news/play/view?n4ArticleSN=21)

재현 설계: 지상 인사이드 받기, 발등 받기, 공중 발/허벅지/가슴 받기, 공을 흘려 이동하며 받기를 별개 후보로 준비한다. 모든 수신을 ‘정지한 공을 차는 킥’의 앞부분으로 대체하지 않는다.

### 새 모션과 새 성능은 같은 말이 아니다

2024년 여름 안내는 컨트롤드 스프린트의 터치와 조작 연결을 설명하는 한편, 일부 슛·패스 모션 추가는 시각적 생동감을 위한 변경이라고 구분했다. 그러므로 새 자세가 보인다는 이유만으로 패스 성공률이나 슛 파워 규칙이 바뀌었다고 추론하면 안 된다. [2024 여름 공식 안내](https://fconline.nexon.com/news/notice/view?n4ArticleSN=4865)

## 3. EA가 실제 공개한 애니메이션 기술

| 자료 | 확인한 내용 | 이번 재현에 가져올 질문 |
|---|---|---|
| [FIFA Animation Warping, GDC 2010](https://gdcvault.com/play/1012580/Animation-Warping-for-Responsiveness-in) | 턴을 실행 중 수정하고, 정해진 시간·공간 목표에 맞추는 방법을 발표 | 이미 있는 턴/킥을 어느 범위까지 변형할 수 있는가? |
| [N-teract, GDC 2017](https://www.gdcvault.com/play/1024015/EA-Presents-N-teract-Next) | 여러 인물의 동작 조건과 정렬을 제작 도구로 구성 | 경합하는 두 명이 공유할 좌표와 접촉 시각은 무엇인가? |

이 다섯 자료는 **공식 발표 초록을 확인한 범위**다. 강연 전체를 시청하거나 내부 구현을 복원했다고 주장하지 않는다. 특히 GDC 2023 페이지는 직접 열기가 시간 초과되어 공식 검색 색인의 초록으로 확인했다.

더 직접적인 제품 설명은 [FC 26 반응성 노트](https://www.ea.com/games/ea-sports-fc/fc-26/news/pitch-notes-fc26-gameplay-responsiveness-update)에 있다. 공과의 거리, 이동 각도, 속도에 따라 모션을 선택하며, 특정 상황의 데이터가 부족하면 더 긴 모션을 쓰거나 위치를 맞추느라 기다릴 수 있다고 설명한다. 전환 분기와 발 선택도 수정 대상이다. 이 설명은 **클립을 적게 가진 상태에서 보간만 늘리는 방법의 한계**를 이해하는 데 유용하다. FCO의 동일 구현을 증명하는 자료는 아니다.

[FIFA 22](https://www.ea.com/games/fifa/pitch-notes/news/pitch-notes-fifa-22-gameplay-deep-dive?cid=69434&ts=1750193738926)는 공에 접근하는 보폭 조정과 함께 캡처한 공중 경합을 설명한다. [FIFA 23](https://www.ea.com/news/pitch-notes-fifa-23-gameplay-deep-dive)은 터치 사이의 움직임과 수비 조키 동작까지 학습 기반 생성의 적용 범위를 넓혔다. HyperMotion·ML-Flow·ML-Jockey를 FCO의 엔진 이름이나 확인된 기능으로 적으면 안 된다.

## 4. 자연스러움을 만드는 요소별 구현 후보

이 절은 재현을 위한 설계 제안이다.

| 요소 | 해결할 문제 | 축구에서 적용할 곳 |
|---|---|---|
| 상황별 원본 클립 | 필요한 자세 자체가 없음 | 질주 출발, 급정지, 큰 턴, 인사이드 패스, 발리 |
| 위상 정렬 | 왼발 지지 중 오른발 지지 자세로 바뀜 | 걷기↔달리기, 드리블↔조키 |
| 모션 매칭 | 현재 자세와 다음 이동에 맞는 후보 선택 | 연속 이동, 급격한 방향 입력 |
| 전환 비용·유지 편향 | 매번 다른 후보로 갈아타서 떨림 | 작은 스틱 흔들림, 비슷한 달리기 후보 |
| 관성 전환 | 위치는 이어져도 속도가 갑자기 달라짐 | 달리기→킥, 태클→회복 |
| 시간 보정 | 동작의 발 접촉과 공 도착 시각 불일치 | 논스톱, 이동 중 패스, 헤더 |
| 루트 이동 보정 | 접촉 위치에 몸이 도달하지 못함 | 받기, 태클, 선방 |
| 보폭 보정 | 이동 거리와 발의 스트로크 불일치 | 빠른 달리기, 짧은 드리블 |
| 접지 제약 | 디딤발이 잔디 위에서 밀림 | 턴, 급정지, 킥 지지발 |
| 리타기팅 | 키·다리 길이에 따라 공을 놓침 | 여러 체형의 선수 공유 동작 |
| 두 인물 동기화 | 몸싸움에서 손·어깨가 서로 빗나감 | 어깨 경합, 공중 경합 |
| 시간축 정렬 | 캐릭터·공·행동 상태가 다른 시점을 표시 | 온라인 화면, 리플레이 |

모션 매칭의 구조는 [저자 공개 구현](https://github.com/orangeduck/Motion-Matching)과 [Epic 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine)에서 확인할 수 있다. 전환은 [관성 전환 발표](https://www.gdcvault.com/play/1025331/Inertialization), 발과 물리 이동체의 관계는 [Code vs Data Driven Displacement](https://theorangeduck.com/page/code-vs-data-driven-displacement)가 특히 유용하다.

### 동작 선택 비용의 제안

가중치는 FC 온라인의 수치가 아니라 향후 실험으로 정할 값이다.

```text
먼저 불가능한 후보를 제외:
  행동 종류 / 허용된 발 / 공 높이 / 도달 범위 / 전환 가능 구간

남은 후보의 비용:
  현재 관절 위치·속도 차이
  + 미래 이동 궤적 차이
  + 지지발 상태 불일치
  + 예상 공 접촉 위치·시각 차이
  + 목표 방향 차이
  + 과도한 모션 변형 비용
  + 현재 후보를 버리는 전환 비용

후보가 없으면:
  추가 제어 터치 / 준비 스텝 / 다른 발 / 동작 실패 중
  해당 기준 상황에서 관찰된 처리를 선택
```

위치(m), 속도(m/s), 방향(rad), 시간(s)을 정규화하지 않고 단순히 더하면 한 특성이 검색을 지배한다. 공개 구현의 `database_search`도 쿼리를 데이터베이스 기준으로 정규화한다. [실제 검색 코드](https://github.com/orangeduck/Motion-Matching/blob/main/database.h)

### 발을 고정해도 무릎과 골반이 자연스러워야 한다

접지 중에는 발의 월드 위치를 유지하되, 다리가 닿지 않는 순간까지 억지로 고정하지 않는다. 체중 이동과 골반 높이, 무릎이 접히는 방향, 뒤꿈치가 먼저 들리는 구간을 함께 다룬다. 고정과 해제 사이에도 속도 연속성을 유지해야 한다. [접지 전환 공개 코드](https://github.com/orangeduck/Motion-Matching/blob/main/controller.cpp), [ozz의 두 관절 IK 샘플](https://guillaumeblanc.github.io/ozz-animation/samples/foot_ik/)

발 높이·속도로 접지를 추정하는 방법은 출발점이다. 모든 모션에 같은 임계값을 쓰면 부정확할 수 있다. [UnderPressure 연구](https://arxiv.org/abs/2208.04598)는 접지 라벨과 반력 추정, 발 미끄러짐 정리를 별도의 문제로 다룬다.

### 보폭과 재생 속도를 구분한다

같은 클립을 두 배 빠르게 재생하면 다리뿐 아니라 팔·머리·몸통까지 두 배 빠르게 움직인다. 빠른 질주를 만들 때 보폭을 늘리는 것과 재생 시간을 줄이는 것은 시각적으로 다르다. [보폭 보정 문서](https://dev.epicgames.com/documentation/en-us/unreal-engine/pose-warping-in-unreal-engine)

정지 동작에서는 남은 거리와 클립 진행률의 대응 곡선이 유용하다. 시간만 흘려 정지 포즈를 재생하면서 몸은 이미 멈춰 있으면 발이 미끄러진다. [Distance Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/distance-matching-in-unreal-engine)

### ‘AI 모션’을 먼저 넣을 이유는 없다

[DeepPhase](https://www.ea.com/news/deepphase-periodic-autoencoders-learning-motion-phase-manifolds)는 축구 드리블을 포함한 동작 합성의 연구 근거이고, [PFNN](https://theorangeduck.com/page/phase-functioned-neural-networks-character-control)과 [Learned Motion Matching](https://theorangeduck.com/page/learned-motion-matching)은 중요한 비교 대상이다. 하지만 목표 게임과 다른 동작 데이터로 학습하면 그 데이터의 움직임을 학습한다. 우선 기준 동작·접촉·전환 조건을 확보하고 단순한 검색으로 오차를 줄인 다음, 데이터 규모와 필요성에 맞춰 학습형 접근을 검토하는 편이 낫다.

## 5. 똑같이 만들기 위해 분리해서 모아야 할 동작

아래는 **우리의 확보·검증 목록**이며 FC 온라인 원본 클립 개수나 내부 분류를 뜻하지 않는다.

| 출발 | 앞/옆/뒤, 첫 지지발 좌/우 | 상체 선행 기울기, 첫 2~3걸음 |

| 감속·정지 | 속도별, 공 유무 | 디딤발 순서, 무게중심 낮춤, 정지까지 거리 |
| 작은 턴 | 좌우 30/45/60도 부근 | 몸통과 골반 회전 시차 |

| 지상 첫 터치 | 공이 앞/옆/뒤에서 진입 | 받는 면, 감속, 다음 이동 방향 |
| 공중 첫 터치 | 발/허벅지/가슴, 점프 여부 | 접촉 높이, 완충, 착지 후 연계 |
| 땅볼 패스 | 정지/이동/역방향/원터치 | 디딤발, 발 안쪽 방향, 짧은 후속 스윙 |

| 공중 슛 | 헤더/발리/반발리 | 공 도착 예측, 점프 시각, 상체/발 접촉 |

| 차단·태클 | 발 뻗기/서서/슬라이딩/헛발 | 도달 가능 범위, 충돌 시각, 회복 길이 |
| 몸싸움 | 어깨/등지기/공중 경합 | 두 사람의 상대 좌표와 지지발 |
| 골키퍼 | 준비/사이드스텝/캐치/펀칭/다이빙/기상 | 예비 스텝, 손의 목표점, 공 고정/튕김 전환 |
| 개인기 | 좌우/주발/진입 속도/공 거리 | 여러 접촉 이벤트와 취소 가능 구간 |
| 세트피스 | 도움닫기/페이크/킥 종류 | 공이 정지한 상태의 특수한 자세와 접촉 |
| 넘어짐·회복·세리머니 | 충돌 방향/누운 방향/참여 인원 | 바닥 접촉, 일어날 발, 타 캐릭터와 정렬 |

오른발 클립을 좌우 반전하면 왼발 자료의 초안을 만들 수는 있다. 특정 선수 고유의 자세나 좌우 비대칭까지 같아졌다고 볼 수는 없다. 몸싸움과 세리머니도 두 사람이 각자 모션을 재생하는 것만으로 접촉 위치가 맞지는 않는다.

## 6. 현재 프로젝트를 새로 검사한 결과

검사 시각: `2026-09-22T06:09:15Z`. 검사 대상 11개 파일의 해시와 당시 파일 사본을 보관했다. 읽기 전후 해시가 같아 검사 실행 중 파일이 바뀌지 않았음을 확인했다. 이전 종합 보고서 이후 코드가 바뀌었으므로 **현재 모션 상태는 이 절의 스냅샷을 우선**한다.

이미 들어 있는 기능: 월드 위치를 이용한 발 고정, 두 관절 IK, 접촉 대상에 대한 킥 발 보정, 상황에 따른 발 선택과 왼발 모션 반전, 렌더 자세의 쿼터니언 보간, 스킨을 입힌 팔다리, 로컬 화면 보간과 행동 시간 보간. 이번 조사에서 추가한 기능이 아니라 읽을 당시 존재하던 코드다.

### 기본 캡처 데이터의 범위

| 항목 | 달리기 | 킥 |
|---|---:|---:|
| 원본 | CMU 09_01 | CMU 10_01 |
| 저장 프레임 수 | 45 | 46 |
| 클립 길이 | 0.7333초 | 0.7500초 |
| 저장 샘플 간격 | 60Hz | 60Hz |
| 한 프레임 성분 수 | 34 | 34 |
| 접촉 메타데이터 | 0.9167초 | 0.3167초 |

34개 값은 힙 높이 하나와 11개 관절의 Euler 회전 세 값씩이다. 원래의 수평 루트 이동·진행 방향·독립적인 발목/발가락 회전·접지 곡선은 이 출력 형식에 없다. 절차적 동작은 더 있지만 **독립된 캡처 원본 계열은 둘**이다. [원본 데이터 목록](https://mocap.cs.cmu.edu/search.php)

### 확인된 한계와 의미

1. **킥 원본을 슛·패스·스루·로빙에서 공유한다.** 가중치와 시간 배치는 다르지만 각 행동의 고유한 원본 체중 이동은 없다. 팔·몸통·디딤발까지 다르게 만들려면 데이터 계열을 늘려야 한다.
2. **리타기팅에서 뼈 방향으로 회전을 재구성한다.** `setFromUnitVectors`만으로는 해당 뼈의 길이 방향을 축으로 하는 원본 비틀림까지 복구되지 않는다. 같은 다리 방향이어도 발등/인사이드의 면이 달라지는 문제와 연결된다.
3. **접촉 시각은 실측 충돌 라벨이 아니다.** 변환기는 낮은 높이에 있는 정강이 끝의 전방 속도 최대점을 찾아 접촉으로 간주한다. 원본 공의 위치를 추적해 검증한 접촉 시각이 아니다. 값 0.3167초를 FC 온라인 접촉 시간으로 써서는 안 된다.
4. **달리기의 접촉 메타데이터가 클립 밖이다.** 0.7333초 클립에 0.9167초 값이 있다. 현재 달리기 재생에서는 이 값을 사용하지 않으므로 즉시 런타임 오류라는 뜻은 아니다. 범용 이벤트 형식으로 바꾸기 전에 데이터 검증이 필요하다.
5. **루프 경계가 완전히 일치하지 않는다.** 달리기의 첫/끝 자세를 쿼터니언 각도로 비교하면 오른쪽 아래팔 8.14도, 머리 4.66도 차이가 있다. 변환기의 루프 탐색 비용은 팔을 제외한다. 렌더에서 눈에 띄는 튐인지까지 이번 검사로 판정한 것은 아니다. [루프 경계 보정 참고](https://theorangeduck.com/page/creating-looping-animations-motion-capture)
6. **최종 관절은 쿼터니언으로 보간하지만 원본 샘플러와 캡처 혼합은 축별 Euler 보간이다.** 최종 한 단계의 보간을 바꾸는 것과 전체 데이터·블렌딩 파이프라인을 바꾸는 것은 다르다.
7. **접지 여부가 원본 접촉 라벨보다 주기 규칙에 의존한다.** 현재 `cycle < .5`, 발 높이, 도달 길이 등의 조건으로 발을 고정한다. 원본 캡처의 실제 접지 구간과 같은지는 아직 측정하지 않았다.
8. **공 접촉 판정은 논리적 발 위치, 시각 보정은 관절 IK다.** 별도 구조 자체는 합리적이지만 둘이 공유하는 목표·시각의 오차를 측정해야 한다. 실제 렌더 메시 충돌을 물리 판정에 반드시 쓸 필요는 없다.

### 재생 속도에서 나오는 차이

검사 시점 보행 주기는 이동 거리 기반으로 진행한다. 2·4·6·8m/s에서 계산한 달리기 원본 대비 재생 배율은 다음과 같다. 9m/s를 넘는 구간은 이 표에 포함하지 않았다.

| 이동 속도 | 한 주기의 이동 거리 | 한 주기 시간 | 원본 대비 재생 속도 |
|---:|---:|---:|---:|
| 2m/s | 1.49m | 0.7450초 | 0.984배 |
| 4m/s | 1.93m | 0.4825초 | 1.520배 |
| 6m/s | 2.37m | 0.3950초 | 1.857배 |
| 8m/s | 2.81m | 0.3513초 | 2.088배 |

이는 현재 코드 수식의 계산값이며 FCO 보폭 측정값이 아니다. 빠른 속도에서 원본의 팔과 상체 움직임도 빨라지는 요인이므로, 보폭 보정과 별도의 질주 클립을 비교할 필요가 있다.

킥 원본에서 접촉 전 구간 0.3167초를 0.18초에 맞추면 약 1.759배, 0.24초에 맞추면 약 1.319배로 재생된다. 두 액션의 동작 인상이 다른 이유 일부를 설명하지만, 이것만으로 실제 접촉 지연을 계산할 수는 없다. 게임은 도달·정렬 조건에 따라 접촉 일정을 뒤로 미룰 수 있다.

관절 추종 감쇠 상수 18과 28의 정지 목표 90% 도달 시간은 각각 약 127.9ms, 82.2ms다. 이것은 **필터 자체의 수학적 응답**이다. 총 입력 지연이 그만큼이라는 의미가 아니며, 접촉 IK는 이후에 적용된다. [감쇠·관성 전환 참고](https://theorangeduck.com/page/spring-roll-call)

검사 결과는 `local-motion-audit.json`, 원본 당시 내용은 `local-snapshot/`에 있다. 게임 코드 변경이나 전체 플레이 테스트는 이번 조사 범위에 포함하지 않았다.

## 7. 동작 데이터 형식부터 바꿀 때 필요한 항목

아래 구조는 제안이며 추출된 FCO 데이터 형식이 아니다.

```text
clip
  id, source, take, sourceRate, duration, rigVersion
  localRotations: quaternion tracks
  localTranslations: 필요한 관절 트랙
  rootTrajectory: 위치·방향·속도
  contacts: 왼발/오른발/손/공 접촉 구간
  events: 준비 종료, 공 터치, 다음 행동 허용
  tags: 행동·발·진입 속도·공 높이·진입/출구 방향
  markers: 뒤꿈치 접지, 발끝 이탈, 킥 최대 후방점 등
  warpLimits: 시간·이동·회전 보정의 허용 범위
  partnerAnchors: 두 인물 상호작용의 상대 위치
  reference: 기준 영상·구간·관측 신뢰도
```

연속된 긴 캡처는 원본으로 보존하고, 반복 클립과 액션 클립을 파생시킨다. 루프는 자세와 속도를 검사한다. 액션의 시작과 끝이 다르다는 이유만으로 오류로 분류하지 않는다. 접촉 이벤트는 단발과 복수를 모두 표현해야 한다. 개인기는 하나의 ‘kickAt’만으로 충분하지 않다.

키가 다른 선수로 옮길 때는 본 이름뿐 아니라 기준 자세, 힙 높이, 다리 길이, 발바닥 위치, 루트 이동의 스케일을 확인한다. 팔과 다리의 길이를 바꾸고 동일 회전만 복사하면 접촉 공간이 달라진다. [Three.js 리타기팅 옵션](https://threejs.org/docs/pages/module-SkeletonUtils.html)

## 8. 제안하는 실행 순서

```text
입력과 경기 상태
  → 다음 이동·공 궤적 예측
  → 발·높이·전환 구간으로 후보 제한
  → 자세·궤적·접촉 비용으로 후보 선택
  → 공 접촉 목표 시각과 이동 계획 결정
  → 허용 범위 안에서 시간·루트·보폭 보정
  → 관성 전환과 상체 보조 동작
  → 접지·공 접촉·손 접촉 제약 해결
  → 변형된 캐릭터 표시

권위 있는 시뮬레이션:
  동일한 액션 ID·접촉 계획으로 공 반응 이벤트 처리

화면과 리플레이:
  선수·공·액션을 하나의 표시 시각으로 샘플링
```

공 궤적을 예측한 뒤 매 프레임 목표를 완전히 바꾸면 접촉 직전 발이 떨릴 수 있다. 동작별로 어느 시점까지 목표를 갱신할지 정하고, 이후에는 제한된 보정이나 실패 처리를 한다. 반대로 너무 일찍 확정하면 움직이는 공을 못 따라간다. 이 경계는 기준 영상에서 찾아야 하는 핵심 값이다.

다중 캐릭터 경합은 두 액션의 공통 시작 시각과 상대 위치를 갖게 한다. 한쪽이 넘어지거나 입력을 바꿀 때 서로 다른 종료 모션으로 안전하게 빠져나오는 경우도 별도로 준비한다. 이 구조는 [EA의 상호작용 발표](https://www.gdcvault.com/play/1027465/Animation-Summit-Environmental-and-Motion)를 참고한 설계이며 FCO 내부 구조의 확정 설명은 아니다.

## 9. 동일함을 판정하는 측정 방법

‘더 자연스럽다’와 ‘목표 게임과 같다’는 다른 기준이다. 의도적인 과장이나 비현실적인 빠른 턴이 기준 게임에 있다면, 리얼한 축구처럼 고치는 것만으로 복제 목표에 가까워지지는 않는다.

### 영상에서 기록할 값

| 관측 | 기록 방법 | 한계 |
|---|---|---|
| 동작 길이 | 실제 프레젠테이션 타임스탬프와 프레임으로 시작·접촉·종료 기록 | 슬로모션·편집 구간은 별도 표시 |
| 입력 반응 | 입력 표시가 있는 원본에서 입력 시점과 첫 반응 비교 | 입력 표시 없는 공식 영상만으로 측정 불가 |
| 발 접지 | 발바닥의 지면상 이동, 접지·이탈 프레임 표시 | 방송 카메라 이동을 먼저 보정해야 함 |
| 턴 | 몸 방향·이동 방향·공 방향을 따로 추적 | 화면상의 각도가 월드 각도와 같지 않음 |
| 공 접촉 | 공과 발/손/머리의 가장 가까운 시각, 공 속도 변화 | 가림·모션 블러가 있으면 구간으로 표시 |
| 자세 | 발목·무릎·골반·흉곽·어깨·손목의 투영 위치 | 한 시점 영상만으로 관절의 깊이와 비틀림을 확정할 수 없음 |
| 연계 | 첫 행동의 접촉 이후 다음 행동 시작까지 시간 | 입력 유지·입력 버퍼 조건을 함께 기록해야 함 |

카메라가 다른 두 영상을 화면 좌표로 곧바로 비교하지 않는다. 가능하면 고정 카메라나 동일한 리플레이 카메라를 사용한다. 경기장 선으로 지면 좌표를 맞추는 보정은 지면상의 위치 비교에만 적용한다. 공중에 뜬 발·머리의 3D 위치는 지면 변환만으로 복원되지 않는다.

60fps 원본의 한 프레임 간격은 약 16.67ms다. 하나의 이벤트 위치는 인접 프레임 사이의 구간으로 다루고, 두 이벤트 사이 시간에는 양쪽 경계의 불확실성이 들어간다. 프레임 수를 세어 임의로 1ms 단위의 정확도를 주장하지 않는다.

### 우리 프로젝트에서 직접 기록할 값

`inputTime, acceptedTime, motionStart, commitTime, plannedContact, actualContact, ballRelease, nextActionAllowed, clipId, clipTime, selectedFoot, warpAmount, plantError, contactError`.

접촉 이벤트 ID는 한 번만 실행되는지 확인한다. 고정 시간 간격이 이벤트 시각을 건너뛰어도 실행되도록 이전 시각과 현재 시각 사이의 통과를 검사한다. 리플레이 재생 속도를 바꾸더라도 시뮬레이션 결과 자체가 바뀌면 안 된다.

### 초기 검증 순서

1. 동일 선수·체형·카메라·공 상태를 고정한다.
2. 정지 패스, 정지 슛, 직선 달리기, 90도 턴, 180도 턴부터 기준 장면을 만든다.
3. 접촉 시점으로 정렬한 비교와, 입력 시점으로 정렬한 비교를 따로 한다. 전자만 하면 입력 지연을 숨길 수 있다.
4. 가장 크게 다른 축이 데이터, 선택, 시간, 접촉, 화면 중 어디인지 분류한다.
5. 한 축을 바꾸고 같은 장면을 재측정한다. 이후 속도·발·진입 방향으로 범위를 넓힌다.
6. 차이가 줄어든 뒤 선수 고유 스타일, 체형, 온라인 지연, 경합으로 확장한다.

`capture-plan.json`은 첫 반복 검사용 96개 조건 슬롯과 확장 항목이다. 슬롯 수는 실제 확보된 영상 수나 EA의 동작 수가 아니다. 수행 불가능한 조합은 억지로 채우지 말고 해당 없음으로 기록한다.

## 10. 재현 작업의 우선순위

| 순서 | 작업 | 완료 증거 |
|---|---|---|
| 1 | 기준 영상·버전·선수·카메라 고정 | 장면별 메타데이터와 원본 구간 |
| 2 | 기존 두 클립의 루트·회전·접촉 데이터 보존 | 변환 전후 오차와 이벤트 검증 |
| 3 | 패스·슛·드리블·큰 턴 원본 계열 분리 | 같은 조건에서 비교할 독립 클립 |
| 4 | 발 선택·접촉 계획·전환 구간 통합 | 지연·발/공 오차를 설명하는 로그 |
| 5 | 접지 해제와 관성 전환 보정 | 턴·정지·킥 연계에서 연속된 발 궤적 |
| 6 | 후보 검색·보정 한계 설정 | 부족한 상황과 선택 실패의 목록 |
| 7 | 첫 터치·공중볼·수비·골키퍼 확장 | 상황별 비교 사례 |
| 8 | 경합·고유 스타일·세리머니 확장 | 둘 이상이 참여하는 접촉·종료 검증 |

현재는 엔진 전체를 교체해야 한다는 근거보다 **동작 원본의 부족과 변환 과정의 정보 손실을 해결해야 한다는 근거가 훨씬 직접적**이다. 현재 렌더링 기술 안에서도 데이터 형식과 접촉 계획을 개선할 수 있다. 엔진 이름만 맞춘다고 자세와 타이밍이 같아지는 것은 아니다.

## 11. 확보한 것과 아직 없는 것

확보: 출처별 적용 범위를 붙인 38개 자료, 공식 비교 페이지 4개의 고유 영상 주소 200개, 해당 주소의 HTTP 응답 검사, 현재 모션 코드 11개 파일의 스냅샷, 원본/변환 클립의 수치 검사, 동작 확보 목록과 재현 측정 규격.

미확보: FCO의 원본 스켈레톤·클립·선택 비용·접지 곡선·정확한 내부 타이밍, 현재 플레이 버전의 동일 조건 반복 캡처. 영상 200개를 모두 시청하거나 프레임별로 계측한 상태도 아니다. 공식 페이지의 설명과 주소를 확인했고 영상 파일 본문은 다운로드하지 않았다. 따라서 수치로 제시한 FCO 입력 지연·관절각·보폭 측정값은 이 문서에 없다.

목표와 동일하다는 판정은 이 자료를 바탕으로 구현한 뒤 기준 장면에서 오차를 측정해야 내릴 수 있다. 이번 조사는 그 판정을 가능하게 할 자료와 작업 기준까지 준비한 것이다.
